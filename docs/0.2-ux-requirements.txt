# HyperSearch 0.2 — исправление интерфейса и улучшение UX

Ты — senior Rust/Windows GUI engineer и UI/UX designer.

Репозиторий:
https://github.com/Noki1945/HyperSearch

Твоя задача — исправить существующий интерфейс HyperSearch 0.2 beta, устранить визуальные ошибки и превратить его в современный, минималистичный файловый менеджер с дизайном, вдохновлённым macOS Tahoe Liquid Glass.

**Важно: функциональность уже реализована. Не создавай её повторно. Сначала изучи текущую архитектуру и исправь существующий GUI.**

## 1. Критические ошибки интерфейса

На реальном скриншоте текущей версии обнаружены следующие проблемы:

1. Белый или почти белый текст на белом фоне.
2. Практически невидимые подписи кнопок.
3. Слабый контраст полей ввода.
4. Несколько перегруженных рядов кнопок.
5. Отсутствие визуальной иерархии.
6. Неправильное отображение списка файлов.
7. Наложение нескольких сообщений в строке состояния.
8. Нечитаемая панель предпросмотра.
9. Несогласованное оформление разных Win32-контролов.
10. Интерфейс не соответствует ожидаемому стилю Liquid Glass.

Эти ошибки должны быть исправлены в первую очередь.

Не ограничивайся изменением нескольких цветов.

Нужно системно переработать тему, отрисовку и компоновку.

## 2. Исправление системы тем

Создай единую систему цветовых токенов:

- WindowBackground
- SurfaceBackground
- GlassSurface
- PrimaryText
- SecondaryText
- DisabledText
- Border
- Accent
- Hover
- Selected
- Warning
- Error

Для светлой темы используй тёмный текст на светлых поверхностях.

Для тёмной темы используй светлый текст на тёмных поверхностях.

Проверь каждый элемент управления:

- Button.
- Edit.
- ComboBox.
- ListView.
- TreeView.
- Static.
- Checkbox.
- Toolbar.
- Tooltip.
- ContextMenu.
- StatusBar.

Обрабатывай необходимые сообщения WM_CTLCOLOR*, WM_THEMECHANGED и WM_SYSCOLORCHANGE.

Учитывай, что стандартные Windows-контролы не всегда корректно наследуют пользовательские цвета.

Не используй прозрачные поверхности, если текст на них теряет читаемость.

Поддержи системный режим высокой контрастности.

Цель — контраст текста не ниже WCAG AA там, где применимо.

## 3. Новый layout главного окна

Полностью переработай компоновку.

### Верхняя панель

Один компактный ряд:

- Назад.
- Вперёд.
- Вверх.
- Адресная строка.
- Поле поиска.
- Кнопка фильтров.
- Кнопка настроек.

Не размещай десятки одинаковых кнопок подряд.

### Боковая панель

Ширина приблизительно 200–240 DIP на обычном настольном экране, адаптивная на маленьких окнах.

Разделы:

Избранное:
- Главная.
- Рабочий стол.
- Документы.
- Загрузки.

Устройства:
- Диски.
- Этот компьютер.

Быстрый доступ:
- Недавние.
- Закреплённые папки.

Используй иконки и небольшие подписи.

### Центральная область

Над списком:

- Компактные фильтры.
- Сортировка.
- Переключатель вида.

Основная часть:

- Имя.
- Расположение.
- Тип.
- Размер, если известен.
- Дата изменения, если известна.

Не показывай пустые колонки без необходимости.

Используй виртуализированный список.

### Правая панель

Предпросмотр метаданных.

Сделай её скрываемой.

По умолчанию открывай только при достаточной ширине окна.

### Нижняя панель

Одна компактная строка состояния.

Не допускай наложения сообщений.

Показывай:

- Количество объектов.
- Состояние индекса.
- При необходимости время последнего поиска.

Подробные диагностические сообщения перенеси в отдельное окно.

## 4. Liquid Glass — правильная реализация

Сейчас проект использует DWM + GDI + стандартные Win32-контролы.

Изучи, достаточно ли этой архитектуры для желаемого визуального результата.

Не считай включение DWM Mica полноценной реализацией Liquid Glass.

Mica и Acrylic могут использоваться как фон, но не решают автоматически проблемы с оформлением кнопок, таблиц, выделения и навигации.

Исследуй варианты:

- Direct2D.
- DirectComposition.
- Windows App SDK / WinUI 3.
- Собственная отрисовка отдельных компонентов.
- Гибридный подход с нативным окном и кастомными контролами.

Сравни их по:

- Расходу RAM.
- CPU в простое.
- Времени запуска.
- GPU-нагрузке.
- Поддержке DPI.
- Accessibility.
- Сложности сопровождения.

Выбери наиболее подходящую архитектуру.

Если стандартные Win32-контролы мешают созданию качественного интерфейса, замени только необходимую часть UI.

Не переписывай поисковый движок.

Не используй Electron или Chromium без серьёзного обоснования.

### Визуальные требования

- Единая система отступов.
- Скруглённые поверхности.
- Аккуратные стеклянные панели.
- Мягкие границы.
- Хорошая читаемость.
- Плавные hover-состояния.
- Красивое выделение файлов.
- Современные иконки.
- Светлая и тёмная темы.
- Минималистичная типографика.

Эффекты должны быть сдержанными.

Не добавляй прозрачность ради прозрачности.

## 5. Проверка реального интерфейса

Это обязательный этап.

Текущая документация подтверждает автоматические и скрытые GUI-тесты, но они не выявили очевидные визуальные проблемы.

Добавь настоящие визуальные проверки.

Если пользователь разрешил захват экрана в среде тестирования:

1. Запусти видимое приложение.
2. Сделай скриншот.
3. Проверь читаемость всех элементов.
4. Проверь расположение контролов.
5. Проверь перекрытия.
6. Исправь ошибки.
7. Повтори проверку.

Если захват экрана запрещён, не обходи запрет. Вместо этого используй тесты геометрии, цветов, состояния контролов и ручной чек-лист для пользователя.

Не утверждай, что интерфейс визуально проверен, если реальной визуальной проверки не было.

Проверь разрешения 1280×720, 1920×1080 и 2560×1440.

Проверь масштабирование 100%, 125%, 150% и 200%.

Проверь уменьшение окна.

Проверь обе темы и системную высокую контрастность.

## 6. Исправление списка файлов

На предоставленном скриншоте видна иконка папки, но текст элементов практически отсутствует.

Проверь:

- Owner-data ListView.
- Unicode-буферы.
- Отрисовку текста.
- Цвета элементов.
- Ширину колонок.
- Правильность LVN_GETDISPINFO.
- Выделение строк.
- Прокрутку.
- Состояние пустого списка.

Добавь явные состояния:

- Загрузка.
- Пустая папка.
- Нет совпадений.
- Ошибка доступа.
- Индекс не загружен.

Пользователь не должен видеть просто пустую белую область без объяснения.

## 7. Статус USN и ошибки

Сейчас внизу появляется сообщение об отказе в доступе OS error 5.

Не выводи длинную диагностическую строку непосредственно в нижней панели.

Создай компактный статус:

- Актуален.
- Проверяется.
- Требует проверки.
- Недоступен.

При нажатии показывай подробности.

Если доступ к USN запрещён, объясняй:

«Поиск по сохранённому индексу доступен, но автоматическая проверка изменений требует дополнительных разрешений».

Предложи:

- Продолжить поиск.
- Обновить индекс доступным способом.
- Посмотреть инструкцию.

Не запускай всё приложение от администратора автоматически.

Исследуй возможность отдельного минимально привилегированного процесса для операций NTFS, требующих повышения прав.

Не запрашивай UAC без конкретного действия пользователя.

## 8. Ускорение анализа хранилища

Согласно STORAGE_ANALYSIS.md, анализ полного снимка из примерно 1,28 млн объектов занимал около 101 секунды.

Улучши пользовательский опыт:

- Быстрая предварительная сводка.
- Постепенное появление результатов.
- Прогресс анализа.
- Отмена.
- Повторное использование корректных сохранённых метаданных.
- Возможность анализировать отдельную папку.
- Приоритет крупных каталогов.

Не обещай точный размер каталога, пока не собраны необходимые данные.

Не смешивай логический и физический размер файлов.

Не удаляй пользовательские файлы.

## 9. Улучшение сортировки

Сейчас сортировка и ранжирование применяются к загруженным страницам.

Исследуй глобальную сортировку результатов.

Добавь возможность сортировать по:

- Имени.
- Типу.
- Расположению.
- Размеру.
- Дате изменения.
- Релевантности.

Не загружай миллионы результатов в RAM только ради сортировки.

Используй ограниченные структуры данных и ленивую обработку там, где это возможно.

Если глобальная сортировка не реализована, явно обозначай ограничение.
