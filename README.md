# HyperSearch 0.2 beta

[Скачать Windows x64 0.2 beta](https://github.com/Noki1945/HyperSearch/releases/tag/v0.2.0-beta.1)

Нативные стеклянные поверхности Windows, отдельные параметры и Spotlight, виртуальные виды файлов, фильтры, ранжирование, метаданные, фоновое обновление USN и локальные отчёты по хранилищу. Инструкция: [BETA-0.2.md](BETA-0.2.md), проверки интерфейса: [UI_PERFORMANCE.md](UI_PERFORMANCE.md), экспорт и приватность: [STORAGE_ANALYSIS.md](STORAGE_ANALYSIS.md). Предыдущая [beta 0.1](https://github.com/Noki1945/HyperSearch/releases/tag/v0.1.0-beta.1) остаётся доступна.

Упрощённый нативный интерфейс Проводника: боковая панель дисков, адресная строка, переходы назад/вверх, поиск в текущей папке или по всему индексу и таблица «Имя / Расположение / Тип». Двойной щелчок открывает папку внутри программы или файл в системном приложении. Инструкция и ограничения: [BETA-0.1.md](BETA-0.1.md).

Готовые таблицы теперь сохраняются на диск: на реальном полном индексе повторная подготовка движка заняла около 1,0 с вместо 3,5 с при построении и сохранении. Fast-кэш — около 302 МБ, дополнительно к 79 МБ исходного снимка. Детали: [CACHE.md](CACHE.md). На время тестирования fast выбран по умолчанию; явные сохранённые настройки другого режима сохраняются.

Проверки и статистика beta: [BETA_TEST_REPORT.md](BETA_TEST_REPORT.md), [CHANGELOG.md](CHANGELOG.md).

Поисковый движок Windows x64: Rust stable, edition 2024, библиотека, CLI и нативный GUI. GUI использует `windows-sys`; модуль отчётов использует `serde`/`serde_json`. Поиск и анализ не изменяют пользовательские файлы; отчёты создаются только по запросу.

## Сборка

Установите stable Rust. Для MSVC нужны Visual Studio Build Tools с C++ и Windows SDK. GNU поддерживает встроенный self-contained linker. Проверенная конфигурация: Rust 1.100.0, Windows x64, GNU.

Готовый локальный exe после сборки находится в `dist/hypersearch.exe`. Если политика PowerShell запрещает скрипты, используйте команды Cargo напрямую без изменения политики:

```powershell
$env:CARGO_TARGET_DIR="$env:LOCALAPPDATA\HyperSearch\build"
# Только для GNU:
$env:RUSTFLAGS='-C link-self-contained=yes'
cargo test --workspace
cargo build --release
& "$env:CARGO_TARGET_DIR\release\hypersearch.exe" --help
```

```powershell
./scripts/build.ps1
./dist/hypersearch.exe index --root 'C:\Documents' --walk
./dist/hypersearch.exe search 'report 2026' --limit 100
./dist/hypersearch.exe search 'report' --mode prefix --ext xlsx
./dist/hypersearch.exe stats
./dist/hypersearch.exe verify
```

Укажите существующий каталог. `index` без `--root` сканирует доступные буквы дисков. Для быстрого NTFS-метода запустите консоль администратором и выполните `index --root 'C:\'`. Если API недоступен, программа сообщает причину и переходит к обходу каталогов. `--walk` принудительно выбирает обход.

`rebuild` перестраивает выбранные корни и заменяет весь предыдущий набор томов. `verify` проверяет формат, контрольную сумму и связи родителей, но не актуальность файлов. Повреждённый индекс отклоняется; восстановление — `rebuild` с нужными корнями. Несколько писателей одного индекса одновременно не поддерживаются.

Данные: `%LOCALAPPDATA%\HyperSearch\index.hsi`; переопределение — `HYPERSEARCH_INDEX`. Индекс содержит имена файлов, поэтому храните его с подходящими правами доступа.

## Поиск

При первом запуске GUI сначала показывает **оценку RAM**, не загружая поисковый индекс. Выберите экономный, сбалансированный, быстрый режим или собственный бюджет в МБ, затем нажмите «Применить и загрузить». Бюджет — ориентир с запасом, не жёсткий лимит Windows; недостаточное значение отклоняется. Выбор сохраняется. Повторный запуск с сохранённым обычным профилем сразу загружает готовые таблицы, а для собственного бюджета сначала повторяет оценку. На полном индексе этого ПК экономный режим занял около 237 МБ памяти процесса, `excel.exe` — около 19–21 мс с путём. См. [режимы и измерения](MEMORY_MODES.md).

CLI: `hypersearch estimate [--budget-mb 384]` считает оценку без загрузки поиска; `hypersearch search excel.exe --memory economy` выбирает профиль. Доступны `economy`, `balanced`, `fast`; библиотечный `SearchIndex::with_mode` принимает `MemoryMode`. По умолчанию библиотека/CLI/новый GUI используют fast для тестирования.

Для поиска по всему компьютеру нажмите в GUI **«Все диски»** и дождитесь индексации, затем введите `excel.exe` в строку поиска. Эта кнопка индексирует корни всех доступных букв дисков; поле каталога не ограничивает уже загруженный поисковый индекс. Его область показывается в строке состояния. CLI: `hypersearch index` без `--root`, затем `hypersearch search excel.exe --mode exact`. Для быстрой полной NTFS-индексации запустите приложение администратором. Уже сохранённый индекс можно искать в обычном GUI; если доступа к USN нет, он явно отображается как снимок с непроверенной актуальностью. Это не подтверждение полноты для отключённых дисков, сетевых ресурсов без буквы или всех альтернативных hard-link имён.

Режимы `--mode exact|prefix|substring`. В substring все слова должны присутствовать в имени. Unicode lowercase поддерживает русский и английский, но это не полная Unicode case folding или NFC. Расширения: запрос `.xlsx` или `--ext xlsx`. `--path DIR` ограничивает область каталогом; точный полный путь файла также допустим. Обычная и расширенная формы путей сопоставляются одинаково.

Результаты упорядочены по внутреннему ID, без семантического ранжирования. Следующая страница — `--after ID` из `next cursor`. Курсор действителен только для неизменного снимка и запроса. Лимит не требует полного подсчёта совпадений. Нулевой лимит возвращает пустую страницу.

Без команды запускается интерактивный поиск; `:quit` завершает его. Это снимок на начало сессии. Показанное время поиска не включает загрузку индекса, построение таблиц, восстановление путей и вывод результатов.

Библиотечный API: `SearchIndex::new(volumes)`, `search(&Query { text, mode, extension, path }, after, limit)`, `path(id)`. Структуры находятся в `crates/engine/src/search.rs`.

## Архитектура

* `filesystem`: обход каталогов; reparse points и junctions сохраняются, но не обходятся. Все доступные hard-link пути сохраняются отдельно. Недоступные объекты и некорректные Unicode-имена отмечаются предупреждениями.
* `indexer` / `ntfs`: документированный `FSCTL_ENUM_USN_DATA`, FRN и Parent FRN, буферы 1 MiB. Полные пути вычисляются только по запросу.
* `search`: общий буфер нормализованных имён и отсортированные ID для точного поиска. В balanced/fast используются адаптивные списки/битовые наборы триграмм; fast дополнительно индексирует короткие запросы. В economy подстроки ищутся линейно по компактным именам. Результаты всех режимов одинаковы.
* `storage`: бинарный формат с версией, FNV-1a для случайной порчи, проверка графа, временный файл + sync + атомарная замена через `MoveFileExW`. Контрольная сумма не защищает от намеренной подделки.
* `monitor`: сохранение Journal ID и следующего USN, инкрементальные изменения по FRN. При разрыве/пересоздании журнала CLI перестраивает соответствующий том; при невозможности перестроения запрос завершается ошибкой.
* `benchmark`: синтетические данные, сравнение с линейным алгоритмом, p50/p95/p99, память и CPU процесса.

NTFS-журнал догоняется перед поисковым запуском. `watch` читает журнал раз в секунду и сохраняет изменившийся снимок. Поисковые таблицы строятся при загрузке, поэтому это ещё не постоянно работающий сервер поиска. Изменения файловой системы после обработанной позиции USN возможны.

Обходной индекс явно обозначается как **снимок без мониторинга**; для обновления нужен `rebuild`. Команда `watch` отказывает для таких индексов.

## Проверки

```powershell
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
./dist/hypersearch.exe benchmark --size 1000000 --iterations 100
foreach ($size in 100000,1000000,5000000,10000000) {
    ./dist/hypersearch.exe benchmark --size $size --iterations 100

```

Для GNU без внешнего MinGW задайте `$env:RUSTFLAGS='-C link-self-contained=yes'` и ASCII-каталог `$env:CARGO_TARGET_DIR="$env:LOCALAPPDATA\HyperSearch\build"`. Скрипт сборки делает это автоматически.

## Ограничения

USN-перечисление возвращает одно имя на FRN. Все дополнительные hard links гарантируются только обходом `--walk`. Изменение hard links в USN требует перестроения. 22 ноября с повышенными правами проверены перечисление C:, живые создание/удаление/переименование/перемещение, изменение пути потомка после переименования папки и восстановление из checkpoint. Недостающие в перечислении родители восстанавливаются по FRN. Реальное переполнение/пересоздание журнала и отключение диска не тестировались. Подробности и ограничения сравнения с Проводником — в [VALIDATION.md](VALIDATION.md).

Короткие подстроки в economy/balanced требуют линейного просмотра; fast использует дополнительные списки. Фильтрация по пути вычисляет пути кандидатов и может быть дорогой. Кэш полных путей, delta/varint-сжатие, interning исходных имён, mmap, многопоточность и ранжирование пока не реализованы. Цель 200 мс подтверждена на описанном наборе запросов, но не является универсальной гарантией. Сравнения с Everything не проводились.

Замеры: [PERFORMANCE.md](PERFORMANCE.md), исходные логи: `benchmarks/`.
