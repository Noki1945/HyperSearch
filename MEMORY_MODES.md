# Режимы памяти — 22 ноября 2026

Обновление beta: по просьбе пользователя fast теперь выбран по умолчанию для тестирования; сохранённый другой явный выбор не отменяется. Повторный запуск с обычным сохранённым профилем пропускает повторный анализ и использует [кэш таблиц](CACHE.md). Ниже сохранены результаты сравнительного исследования и прежняя рекомендация economy как варианта для экономии RAM.

Вместо расхода около 1 ГБ, рассчитанного для прежних таблиц полного индекса, новый движок позволяет выбрать экономию памяти. Данные на диске не менялись: файл индекса около 79 МБ, 1 281 006 поисковых объектов. Сравнение проводится на одном сохранённом индексе; это не новая индексация тома.

## Первый запуск

До подтверждения выбора GUI не вызывает загрузчик полных записей и не создаёт `SearchIndex`. Если индекс уже есть, программа читает его потоком через буфер 64 KiB, сохраняя только количества символов, записей и частоты сочетаний. На новой установке без индекса выполняется обход доступных каталогов для подсчёта; имена и полные пути в поисковой структуре не сохраняются, reparse points не обходятся. Предупреждения о недоступных объектах означают неполный охват и возможную недооценку.

В окне есть «Оценить RAM», выбор режима, поле собственного бюджета в МБ и «Применить и загрузить». Только последняя кнопка разрешает загрузку/построение поиска. Выбор сохраняется рядом с индексом в `index.preferences`; при следующем запуске он применяется после новой оценки. Профиль можно поменять; при переключении предыдущий поисковый индекс освобождается перед построением следующего.

Для своего бюджета выбирается самый быстрый из трёх режимов, который укладывается в расчёт с запасом. Слишком маленькое значение отклоняется с предложением выбрать больше памяти или отдельный каталог. **Это целевой бюджет, а не жёсткий лимит процесса:** Windows, фрагментация, UI, изменения файлов и временные буферы могут увеличить расход. Значения в интерфейсе «МБ» соответствуют 1024² байт. Нельзя гарантировать произвольный бюджет, например 32 МБ, для полного индекса этого компьютера.

Скрытый запуск первого экрана без сохранённых настроек, через 4 с: private bytes 3 993 600, working set 12 259 328. Процесс оставался работающим. Это проверка потребления процесса и логики запуска, не визуальная проверка элементов интерфейса. Захват экрана по просьбе пользователя не включался.

## Что реализовано

1. Нормализованные имена собраны в общую строковую область и таблицу смещений. Миллионы отдельных строковых выделений и копии ключей exact HashMap удалены.
2. Точный поиск использует отсортированный массив ID и двоичный поиск. Для одинаковых имён ID упорядочены, курсоры страниц сохраняют прежний порядок.
3. Доступные векторы уплотняются после построения; расположения записей используют пару `u32` вместо пары `usize`.
4. Posting lists выбирают представление по плотности: редкие — список `u32`, частые — битовый набор. Переход выполняется уже при построении, а не после создания всех больших списков. Это собственная простая адаптивная структура, не реализация формата Roaring.
5. **Экономный:** без триграммных и коротких списков, подстроки ищутся последовательным просмотром компактных нормализованных имён. **Сбалансированный:** добавлены триграммы. **Быстрый:** добавлены также списки для одно-/двухбайтовых запросов.

Все режимы возвращают одинаковые результаты, Unicode-поведение и порядок страниц. Меньший расход памяти не достигается пропуском файлов.

## Измерения на полном индексе компьютера

Release, Windows x64, Ryzen 7 9800X3D, Rust 1.100 GNU. Каждый режим запускался в отдельном процессе. Память снята после загрузки и построения таблиц до выполнения эталонных сравнений. Это память процесса, а не только полезные байты структуры и не пиковый расход. Названия и пути файлов не копировались из тестовых синтетических данных: использован реальный сохранённый индекс C:.

| Режим | Private bytes, десятичные МБ | Working set, МБ | Собственные данные по модели, МБ | Построение таблиц, мс |
|---|---:|---:|---:|---:|
| Экономный | 237,3 | 238,5 | 210,2 | 398,2 |
| Сбалансированный | 391,7 | 389,1 | 343,7 | 1292,9 |
| Быстрый | 502,5 | 497,0 | 442,3 | 2292,1 |

Потоковая оценка перед загрузкой дала 295 / 442 / 550 MiB соответственно. Она намеренно содержит запас и не заменяет фактические замеры. Старое значение «около 1 ГБ» было расчётом для прежнего движка; это не измеренный baseline процесса на том же диске, поэтому точный коэффициент уменьшения относительно него не заявляется.

Точный `excel.exe` во всех режимах: p50 около 0,0006–0,0007 мс. Очень малые времена чувствительны к разрешению таймера.

50 повторов каждого из 9 запросов, первые 100 совпадений, получение полных путей включено; полного подсчёта совпадений нет. Первая страница сверена с линейным эталоном, отдельные тесты сравнивают все страницы и три режима. Время загрузки снимка (410–435 мс), построение, ввод текста и отрисовка GUI исключены из времени запроса. Кэш ОС не сбрасывался.

В перечисленных случаях все режимы уложились в цель **200 мс**, худший p99 экономного — около 43 мс. Это не гарантия для любых компьютеров, индексов, фильтрации по глубоким путям, размера страницы или полного времени реакции интерфейса. Стартовую рекомендацию выбрали экономной, поскольку на этом наборе она экономит около 265 МБ относительно нового быстрого режима при приемлемых задержках. Большие индексы и другие машины требуют повторной проверки.

Логи: `benchmarks/memory-economy.txt`, `benchmarks/memory-balanced.txt`, `benchmarks/memory-fast.txt`. Воспроизведение:

```powershell
cargo build --release -p hypersearch-engine --example profile_memory
profile_memory.exe PATH_TO_INDEX economy
profile_memory.exe PATH_TO_INDEX balanced
profile_memory.exe PATH_TO_INDEX fast
hypersearch estimate --budget-mb 384
hypersearch search excel.exe --memory economy
```

## Исследованные варианты

* Компактные списки и битовые наборы: [Roaring объясняет выбор представления по плотности](https://roaringbitmap.org/about/). Принцип использован в простой собственной структуре; блочный Roaring, delta/varint и сжатие серий можно сравнить отдельно на большем наборе.
* Освобождение лишней ёмкости: [Rust Vec::shrink_to_fit](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.shrink_to_fit). Применено; реальное освобождение зависит от аллокатора.
* Совместное хранение строк: [Arc](https://doc.rust-lang.org/std/sync/struct.Arc.html) позволяет делить одно выделение между владельцами. Здесь выбран более простой общий буфер и смещения, чтобы избежать счётчиков владения для каждого имени.
* Индекс на диске через [memory mapping](https://docs.rs/memmap2/latest/memmap2/struct.Mmap.html): остаётся кандидатом для меньшего начального потребления. Он не гарантирует, что страницы не попадут в RAM, и может добавить page faults и задержки. Пока не добавлен: текущая экономия достигнута без новой зависимости и изменения формата снимка.
