# Проверка Windows — 22 ноября 2026

## Дополнительная проверка 0.2

Новый `crates/engine/examples/incremental_windows.rs` проверен через стандартный RunAs/UAC на реальном C: без изменения настроек журнала. Начальный индекс: 1 288 983 объектов; сканирование и построение вместе — 8960,405 мс. Затем создание: 29,247 мс, переименование: 0,569 мс, перемещение: 0,310 мс, переименование родителя: 0,483 мс, удаление: 0,376 мс. После исходного построения полных перестроений таблиц не было. Менялись только уникальные временные файлы теста; fixture удалён. Лог: `benchmarks/0.2-usn-admin.txt`.

Этот свежий живой набор отличается от старого сохранённого индекса с 1 281 006 объектами, по которому измерены RAM и поиск 0.2. Актуальность старого снимка не предполагается. Скрытая GUI-проверка подтверждает загрузку, виртуальный список, разделы настроек, применение тем и асинхронный ответ о недоступных метаданных без показа окон/захвата экрана: `benchmarks/0.2-gui-smoke.txt`. Физические смешанные DPI/несколько мониторов остаются непроверенными на имеющейся конфигурации с одним экраном 96 DPI.

Более позднее обновление движка добавило выбор RAM и уменьшило расход памяти: [MEMORY_MODES.md](MEMORY_MODES.md). Ниже сохранены исходные результаты NTFS и глобального поиска; поисковые задержки относятся к версии на момент тех запусков.

## Поиск Excel по всему компьютеру

Проверен глобальный запрос по всем доступным корням букв дисков. Windows обнаружила один диск: C: (NTFS). Через повышенный процесс перечислено 1 281 007 записей, поисковый индекс содержит 1 281 006 объектов без корневой записи. Первоначальное сканирование — 2967,036 мс, сохранение — 188,847 мс, построение таблиц — 2752,397 мс; вся подготовка — 5908,293 мс.

Запрос `excel.exe` выполнен без фильтра каталога. И точный, и подстрочный режим с расширением `exe` нашли один существующий файл: `C:\Program Files\Microsoft Office\root\Office16\EXCEL.EXE`. Существование файла отдельно подтверждено файловой системой.

| Режим | Первый запрос с путём, мс | Повторные p50 / p95 / p99, мс |
|---|---:|---|
| Exact | 0,006900 | 0,000400 / 0,000600 / 0,000800 |
| Substring | 0,200500 | 0,014300 / 0,030400 / 0,040600 |

Это время библиотечного поиска по загруженному индексу; GUI-отрисовка и загрузка не включены. Новый GUI поддерживает кнопку «Все диски». Полный индекс сохранён в стандартном каталоге приложения, поэтому после запуска GUI не ограничен прежним тестовым каталогом. Визуальная проверка этой кнопки не выполнялась: захват экрана по просьбе пользователя остановлен.

Исходный лог: `benchmarks/global-excel.txt`. Воспроизведение: собрать `cargo build --release -p hypersearch-engine --example global_search`, затем запустить `global_search.exe PATH_TO_REPORT` с повышенными правами. Пример заменяет стандартный индекс приложения глобальным. Доступные диски без буквы, отключённые носители и дополнительные hard-link имена не входят в гарантию охвата; это не тест абсолютно всех объектов любых подключений.

## NTFS / USN с повышенными правами

Отдельный исполняемый тест `crates/engine/examples/validate_windows.rs` был запущен через стандартный Windows RunAs/UAC. Обычный процесс возвращал OS error 5; повышенный процесс успешно открыл существующий журнал тома C:. Журнал не создавался, не очищался и не перенастраивался.

На первой проверке обнаружена настоящая ошибка: у записи NTFS отсутствовал родитель среди результатов `FSCTL_ENUM_USN_DATA`. Индекс ошибочно считался повреждённым. Исправление: только для отсутствующих родителей выполняются документированные `OpenFileById`, `GetFinalPathNameByHandleW` и чтение идентификатора родительского каталога. Вызовы получения полного пути для каждого файла не добавлены. Ошибки проверки графа теперь содержат причину и FRN вместо общего сообщения.

После исправления:

| Проверка | Результат |
|---|---|
| Открытие/чтение метаданных USN | PASS |
| Перечисление NTFS | PASS: 1 280 634 записи за 2945,161 мс |
| Создание файла с кириллицей | PASS |
| Переименование файла | PASS |
| Перемещение между каталогами | PASS |
| Переименование родительского каталога, путь потомка | PASS |
| Сохранение/загрузка позиции + удаление файла | PASS |
| Отклонение неверного Journal ID | PASS |
| Отклонение просроченной позиции | PASS |
| Удаление каталогов и итоговая проверка графа | PASS |

Replay одного пакета по полному индексу занял 48–78 мс. Это время чтения/применения событий, не задержка поискового запроса. В него входит построение FRN lookup на каждом пакете; дальнейшее ускорение мониторинга требует сохранения этого lookup между пакетами.

Проверка неверного ID/просроченной позиции подменяла только сохранённые значения в памяти. Реальное переполнение/пересоздание журнала, отключение диска, аварийное завершение и внезапное отключение питания не имитировались. Успешный тест не снимает известного ограничения дополнительных hard links.

Исходные логи: `benchmarks/ntfs-normal.txt`, `benchmarks/ntfs-admin.txt`.

## Сравнение на одном реальном каталоге

В `%LOCALAPPDATA%\HyperSearch\validation\fixture-20261122` созданы 20 000 реальных маленьких файлов в 100 каталогах. В каждом каталоге — один `hsneedle_report_*.txt`, один `Отчёт_2026_*.txt` и 198 других документов. Файлы созданы специально для теста; это не репрезентативный пользовательский диск. Каталог сохранён для повторения проверки.

HyperSearch использовал обход этого каталога: 569,892 мс, без предупреждений; построение поисковых таблиц — ещё 19,131 мс. Генерация файлов (5851,436 мс) не включена в поиск. Все совпадения получались целиком, без отсечения первыми 100; восстановление полных путей включено.

Проводник был открыт на **том же каталоге**. Использованы AQS-фильтры `System.FileName:~="hsneedle"`, `System.FileName:~="отчёт"`, `System.FileName:~="hsabsent"`, чтобы искать именно подстроку имени. Визуально и через accessibility проверены имена результатов и количество в строке состояния.

| Запрос | HyperSearch: найдено | Проводник: найдено | HyperSearch p50 с путями, мс | Проводник: Enter → наблюдение готового окна, мс |
|---|---:|---:|---:|---:|
| hsneedle | 100 | 100 | 0,0191 | 430,0093 |
| отчёт | 100 | 100 | 0,0155 | 418,9257 |
| hsabsent | 0 | 0 | 0,0001 | 321,4011 |

**Последние два столбца измеряют разные уровни и не дают коэффициент ускорения.** HyperSearch — библиотечный запрос в памяти, 100 повторов, без UI. Проводник — один UI-запуск на запрос, время включает отправку клавиши, накладные расходы Computer Use, accessibility и снимок экрана. Это верхняя граница времени готовности результата к моменту наблюдения, а не точная задержка поискового движка Проводника. После ввода текст некоторое время находился в поле до Enter; влияние предварительного разбора/кэширования не исключено. Проверено количество и видимые имена, а не полный набор путей Проводника через API.

Файловый кэш Windows не сбрасывался. Настройки Windows Search не изменялись; включение каталога в системный индекс отдельно не подтверждалось. Полноценный холодный/прогретый UI-бенчмарк обоих приложений с одинаковой инструментальной погрешностью ещё нужен. На основании этих наблюдений нельзя честно утверждать «HyperSearch быстрее Проводника в N раз».

Исходные логи: `benchmarks/real-files.txt`, `benchmarks/explorer-real-files.json`.

## Повторение

```powershell
cargo build --release -p hypersearch-engine --example validate_windows
# Из обычной консоли; путь fixture должен быть отдельным тестовым каталогом:
validate_windows.exe --dataset C:\MyValidationFixture --report real-files.txt
# Из консоли администратора:
validate_windows.exe --ntfs C:\ --report ntfs-admin.txt
```

Пример находится в каталоге `release/examples` выбранного Cargo target directory. GNU-сборка использовала `RUSTFLAGS=-C link-self-contained=yes` и ASCII-каталог сборки. NTFS-тест создаёт собственный уникальный временный каталог; при успехе удаляет его, при ошибке оставляет для диагностики. Перечисление тома и снимок для resume могут требовать сотни мегабайт RAM и временного места.

Документация API: [OpenFileById](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-openfilebyid), [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew). Параметры ограничения поиска Проводника описаны в [Windows Search](https://learn.microsoft.com/en-us/windows/win32/search/getting-started-with-parameter-value-arguments).
